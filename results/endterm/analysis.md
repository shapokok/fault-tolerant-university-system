## Discussion, limitations, and lessons learned

1. **Retry budget longer than the caller's timeout (measured weakness, not fixed).** With the database tables locked for 30 s, endterm reached 81.6% against 79.8% for the baseline: almost no gain. Every failed request in the endterm runs ended at the client's 10 s timeout (median 10018 ms, 550 requests). The service tries up to 3 times, and each try waits 2 s on the primary and 2 s on the replica (the lock is replayed there too): about 12 s, longer than the client waits, so even the cached timetable arrives too late. **Proposed fix:** give each request a total deadline below the caller's timeout (for example 8 s for a 10 s client), pass the remaining time to every retry, stop retrying when the budget is used up, and fall back to the cache as soon as the first attempt times out.
2. **Fault tolerance can lower availability while protecting money.** With a slow bank the endterm stack had 90.7% success against 93.6% for the baseline, because the circuit breaker rejects payments at once. The baseline failed the integrity check in every run (money taken for payments it marked failed); the endterm stack passed every run.
3. **Per-IP rate limits and one test machine.** All load generators share one IP, so the limit shapes every load test; the 429 answers are the protection working. Real users have many IPs, and an attack from many IPs would not be slowed down: a per-user limit (by token) would be the next step.
4. **Security choices with costs.** Login fails closed (503) while the primary DB is down, so the lockout cannot be bypassed; tokens already issued keep working. The HS256 secret is shared by all services, so a compromised service could create tokens (RS256 would fix it). No TLS: tokens travel as plain HTTP inside this setup.
5. **Measurement lessons.** A sleeping laptop invalidated the first alert series (now every run is checked for gaps). "Detection" first also counted the stack shutdown after each run; it is now computed only inside the load window. Histogram buckets must match the latencies being measured, otherwise p95 is badly interpolated (a 1 s delay once showed as 2.4 s). Exact latencies always come from the request logs.
6. **Tests found real problems.** The integration test for header spoofing showed that the gateway let a client hide its requests from the access log (`X-Probe`); the regression demo showed that a fault during the login phase stopped the workload. Both were fixed and are covered by tests or checks now.
7. **Limited repetitions and one machine.** 2 repetitions per experiment (alert test 1, plus the E2 series); the standard deviations are therefore rough. Everything ran on one laptop, so load tests share CPU with the system under test (about 82% CPU at 300 users in the endterm stack).
